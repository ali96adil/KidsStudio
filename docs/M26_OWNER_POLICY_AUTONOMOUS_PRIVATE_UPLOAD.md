# M26 — Agent-scheduled PRIVATE YouTube upload under standing owner permission

**GitHub Draft PR #28 only.** Nothing installed on the owner Mac or Pi,
no OAuth consent completed, and no real YouTube upload or publication.
Offline tests use a fake YouTube transport plus real StudioQueue, owner
policy, coordinator, media SHA/readiness and SQLite review records.

## Intended autonomous sequence

1. Owner **once** grants a **standing PRIVATE-only series policy**:
   exact YouTube channel ID, a maximum of 1–5 private uploads per
   rolling 24 hours, and the explicitly declared made-for-kids +
   synthetic-media flags. The owner can PAUSE/revoke it, which bumps
   a policy revision and invalidates *already leased* pre-upload jobs.
   This grant **never** grants public publication or approval of a video.
2. The Mac production line maintains a **private catalogue**, outside
   Git, of ready M8-approved upload plans. For each entry, the
   approved MP4, M8 readiness JSON, exact M8 report SHA and M25
   video/metadata plan must match and be inside one local private
   asset root. These files still need to be generated by a real
   qualified production pipeline; M26 does not fabricate master videos,
   archive signatures, children's audience declarations or ownership.
3. Running the Mac private-upload agent with explicit `--execute` lets
   it ask the Pi to queue one upload per current finalized render.
   Only a Pi **owner-enabled policy**, active series, final
   `EPISODE_APPROVED`, correct completed MP4 SHA, and full M7 QA
   permit enqueue. The Pi limits queued/leased work to one private
   upload per series, enforces the rolling 24-hour cap and uses a unique
   render ID. Attempts are once-only; they cannot silently retry.
4. The Pi assigns a single lease to the dedicated
   `youtube_private_upload` worker identity through existing
   authenticated TLS. The uploader checks exact Pi job fields against
   the private Mac catalogue, then calls
   `private-upload-lease-check` to re-validate policy revision,
   current render, paused state and generation.
5. M25 hashes MP4 and report again and commits `STARTED` to the
   Mac private SQLite journal. A **second live Pi lease/policy check**
   runs immediately after journal reservation and before any
   `videos.insert` network call. A stale, cancelled or paused
   policy stops the upload; STARTED stays quarantined, never retried.
6. If permitted, M25 starts resumable YouTube Data API upload,
   explicitly marks PRIVATE, suppresses subscriber notifications,
   checks the exact intended channel and video's privacy using OAuth
   and waits for **successful processing** before handoff.
   Pi lease heartbeats run during the operation.
7. An authenticated Mac worker reports the immutable private result
   to Pi `complete-private-upload`. The Pi verifies current lease,
   exact approved master/channel/series/episode and still-enabled
   owner policy. If and only if `ready_for_owner_review=true` and
   processing succeeded, the same SQLite transaction completes the
   upload job **and** inserts a versioned M24
   `PRIVATE_AWAITING_OWNER_REVIEW` item with video ID.
   The owner then sees it in the protected review UI, watches the
   PRIVATE video and chooses APPROVE, APPROVE_WITH_NOTES or
   REQUEST_CHANGES. None changes YouTube public visibility.

If YouTube acknowledges the upload but processing is pending, M26
records `YOUTUBE_PRIVATE_PROCESSING_PENDING` and **does not put it
in the owner review queue yet**. Future agent-based status polls can
recheck this exact uploaded ID without reupload; currently M25
`--verify-existing` is a separate opt-in step, and importing a
verified status into M24 requires an explicit owner transfer.

If the network/upload outcome is ambiguous, the Pi lease is lost, or
the Pi receipt ACK fails, the job is quarantined for manual
reconciliation. A real upload may already exist on YouTube; do NOT
enqueue a fresh copy. Review the private local journal and YouTube
Studio and reconcile before continuing.

## Owner controls, future local deployment only

First initialize schema on Pi (must already have SeriesManager and M24
owner-review tables initialized):

```sh
studio-private-policy --db /PRIVATE/studio.sqlite init
```

Grant one series, channel and bounded daily budget, using the actual
owner-selected children's/synthetic-media classification:

```sh
studio-private-policy --db /PRIVATE/studio.sqlite grant colors-ar \
  --channel-id EXACT_UC_CHANNEL_ID \
  --max-uploads-24h 1 \
  --made-for-kids --contains-synthetic-media \
  --owner-note "Allow one AI-produced private preview daily; never auto-publish"
```

Pause (also fences a previously leased worker's future action):

```sh
studio-private-policy --db /PRIVATE/studio.sqlite pause colors-ar
```

Configure a *dedicated* coordinator worker identity with only
`youtube_private_upload` capability, its own independently generated
long bearer token, and a trusted Pi TLS certificate.

Mac private catalogue example **(paths are placeholders)**:

```json
{
  "schema_version": 1,
  "private_root": "/PRIVATE/KidsStudio",
  "entries": [{
    "plan": "/PRIVATE/KidsStudio/upload_plan.json",
    "media": "/PRIVATE/KidsStudio/episode_master.mp4",
    "readiness": "/PRIVATE/KidsStudio/M8_ready.json",
    "readiness_sha256": "EXACT_REAL_M8_REPORT_SHA256"
  }]
}
```

On Mac: default dry run merely validates the local catalogue
(without OAuth, network or queue claim). An explicit `--execute`
with trusted TLS Pi URL, dedicated worker ID and private upload
journal begins one eligible action. It expects
`KIDS_STUDIO_PRIVATE_UPLOAD_PI_TOKEN` and
`KIDS_STUDIO_YOUTUBE_OAUTH_ACCESS_TOKEN` from the Mac's protected
environment and a valid CA chain. No tokens are saved to Git.

```sh
studio-private-upload-agent \
  --pi https://PRIVATE_PI_HOST:8765 \
  --worker-id mac-private-uploader \
  --ca-file /PRIVATE/pi-ca.pem \
  --catalogue /PRIVATE/KidsStudio/private_catalogue.json \
  --journal /PRIVATE/KidsStudio/private_uploads.sqlite
```

Only after owner device/Google qualification, add `--execute` to
perform **one** task per invocation. A scheduled local service can
invoke it periodically, but this project has NOT installed a scheduler,
set up tokens or connected YouTube yet.

## Enforced non-goals

- **No PUBLIC**, no UNLISTED, no scheduled publication endpoint.
- No automatic post-upload owner approval; user's final decision is
  still mandatory before any future, separately authorized public release.
- No Google OAuth browser consent / refresh-token provisioning. The
  Mac needs a real, current OAuth access token and an authorized
  YouTube Data API project before any device test.
- Earlier M7/M8 and M23 gates still require human owner attestations.
  **M26 is not yet fully unattended production.** Upcoming work should
  replace unnecessary internal human signoffs with independent, logged
  AI QA agents while retaining objectively verifiable file rights,
  full technical checks and the **owner's post-upload final review**.
- The Pi receives worker assertions over authenticated TLS but no
  Google cryptographic proof; real Google platform privacy can change
  later. The owner-review UI reports evidence *at verification time*
  and does not claim perpetual Private status.
- Retries after uncertain network outcomes are deliberately disabled;
  unattended recovery and Pi-clock drift are not solved by this step.
